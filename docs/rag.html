Retrieval-Augmented Generation

How classic RAG works, when it shines, and what it costs.

What Is RAG?

Retrieval-Augmented Generation (RAG) combines information retrieval with large language models. Instead of relying solely on the model's training data, RAG first retrieves relevant documents from an external knowledge base, then feeds those documents to the LLM as context for generating an answer.

This approach grounds the LLM's output in real, verifiable sources — critical for domains like technical documentation, legal texts, or enterprise knowledge bases where accuracy matters and hallucinations are costly.

📚

Think of it as an open-book exam

A closed-book LLM answers from memory and may confidently invent details. RAG hands the model the relevant pages first, then asks it to answer using only what is in front of it, citing where each fact came from. Better grounding, fewer hallucinations.

A Worked Example

What a single question actually looks like as it moves through the pipeline.

Query
“How do I enable versioning on an Amazon S3 bucket?”
Retrieved
Top-5 chunks ranked by cosine similarity. The two most relevant:
[1] S3/userguide/Versioning.html — “Versioning keeps multiple variants of an object… set the bucket versioning state with PutBucketVersioning.”
[3] S3/userguide/manage-versioning-examples.html — console and CLI steps.
Answer
Set the bucket’s versioning state to Enabled — in the console under Bucket → Properties → Bucket Versioning, or via aws s3api put-bucket-versioning. After that, S3 retains every version of each object. Sources: [1], [3]

The model only sees the retrieved chunks, not the whole knowledge base. If the right passage is not in the top-K, RAG cannot recover it. That is why retrieval quality sets the ceiling on answer quality.

Cost Model

Every question incurs the full pipeline cost — embedding call + vector search + LLM generation + judge evaluation. With Nemotron Nano 9B via OpenRouter ($0.30 input / $1.20 output per 1M tokens), costs are dramatically lower than frontier models.

Limitations

⚠

Every query is expensive

No caching — repeated questions pay the full cost every time. For high-traffic scenarios, this adds up fast.

⏱

Latency is bounded by LLM

p50 of ~5 seconds per question, dominated by LLM inference time. Vector search is fast (~100ms), but generation takes 3-15 seconds.

🎯

Quality depends on retrieval

If the right chunk isn't in the top-K results, the LLM can't answer. Mean judge score of 0.650 reflects this — some questions require multi-hop reasoning.

📊

No knowledge of past queries

Each question is handled independently. There's no mechanism to learn from prior answers or detect repeated questions.
