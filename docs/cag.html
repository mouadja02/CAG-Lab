Cache-Augmented Generation

Adding a semantic cache layer to RAG — same quality, fraction of the cost and latency.

What Is CAG?

Cache-Augmented Generation (CAG) extends classic RAG with a semantic vector cache. Before running the expensive retrieval + generation pipeline, the system checks if a semantically similar question was already answered. If so, it returns the cached answer instantly — skipping retrieval and generation entirely.

The cache uses Redis vector search with HNSW indexing. Each stored entry contains the query embedding, the generated answer, cited sources, model info, a creation timestamp, and a TTL. Lookup compares the new query's embedding against the nearest cached entry and returns a HIT only if cosine similarity is at or above a configurable threshold (library default 0.92; this lab operates at 0.96, explained below).

🧠

Think of it as a colleague with a good memory

Ask a teammate a question they answered last week and they reply instantly from memory instead of re-reading the docs. CAG does the same: if your question is close enough to one already answered, it reuses that answer. The art is deciding what counts as “close enough” — too loose and you serve the wrong answer, too strict and you rarely reuse anything.

Two recent papers provide the academic foundation for Cache-Augmented Generation:

📖

MeanCache: User-Centric Semantic Caching for LLM Web Services

Gill, Elidrisi, Kalapatapu, Ahmed, Anwar, Gulzar — IEEE IPDPS 2025

Analyzed real-world ChatGPT conversation logs and found that 31% of queries are repeats or near-duplicates (their Figure 1). Introduced MeanCache, a federated-learning approach to semantic caching that achieves 17% higher F-score and 20% better precision than exact-match caching, while using 83% less storage. Their work also encodes context chains to distinguish standalone from conversational queries — critical for avoiding false hits in multi-turn dialogues.

arXiv:2403.02694 →
📖

Don't Do RAG: When Cache-Augmented Generation is All You Need

Chan, Chen, Cheng, Huang — The Web Conference (WWW) 2025

Proposes CAG as a fundamental alternative to RAG for knowledge tasks with constrained document sets. By preloading all relevant resources into the LLM's extended context window and caching runtime parameters, CAG eliminates retrieval latency entirely and avoids document selection errors. Benchmarks show CAG matching or exceeding RAG quality on multiple datasets while being simpler to deploy.

arXiv:2412.15605 →

Our implementation follows the MeanCache architecture — embedding-based semantic matching with a configurable similarity threshold — adapted for a Redis-backed vector search backend rather than federated learning. The core insight is the same: when 3 out of 10 queries are repeats, a semantic cache pays for itself almost immediately.

Architecture Flow

How the Cache Works

Store

When a question misses the cache and goes through full RAG, the result is stored in Redis:

HSET cache:<uuid>
  embedding  <512 float32 bytes>
  answer     <generated text>
  sources    [1, 3]
  model      nemotron-nano-9b-v2
  created_at 1716724800
  source_id  aws-001
  question_text <original query>

EXPIRE cache:<uuid> <ttl_seconds>

Lookup

Before running RAG, embed the query and search for the nearest cached entry:

FT.SEARCH idx:semantic_cache
  "*=>[KNN 1 @embedding $vec AS score]"
  PARAMS 2 vec <512 bytes>
  RETURN 6 answer sources model
         created_at question_text
         source_id
  SORTBY score ASC DIALECT 2

Decision Logic

similarity = 1.0 - cosine_distance
if similarity >= threshold AND not expired:
    return HIT → cached answer (free, ~0.5s)
else:
    return MISS → run full RAG + store result

Hit or Miss: A Worked Example

Suppose the cache already holds one answered question. Here is what happens to two follow-up queries:

Cached
“How do I enable versioning on an Amazon S3 bucket?” — answer + sources already stored
Hit
“What’s the way to turn on versioning for an S3 bucket?”
similarity 0.974 ≥ 0.96 → serve the cached answer in ~0.5 s for ~$0
Miss
“How do I create a CloudFront distribution?”
similarity 0.71 < 0.96 → run full RAG, then store the new answer for next time
ⓘ Why a 0.96 threshold? At the library default of 0.92 the cache accepted borderline matches and occasionally served a confident but wrong answer to troubleshooting and multi-hop questions. Raising the bar to 0.96 drove false positives to 0.0% while still catching 73% of paraphrases. Net effect: answer quality went from −1% to +6% versus RAG.

Cache Metrics

Our benchmark tracks these cache-specific metrics per question:

🎯

Hit Rate

Fraction of workload items served from cache. Target: high on exact repeats and paraphrases.

⚠

False-Positive Rate

Fraction of cache hits where the cached answer belongs to a different question. We catch these via source_id mismatch. Target: as low as possible.

💰

Cost Saved

Generation cost avoided by serving answers from cache. Each hit saves ~$0.00018 in LLM costs.

⏱

Hit vs Miss Latency

Cache hits complete in ~0.5s (embed + Redis KNN). Cache misses take ~5.6s (embed + retrieve + generate).

Redis Vector Search Configuration

FT.CREATE idx:semantic_cache
  ON HASH PREFIX 1 cache:
  SCHEMA
    created_at NUMERIC
    embedding VECTOR HNSW 10 TYPE FLOAT32
      DIM 512
      DISTANCE_METRIC COSINE
      M 64
      EF_CONSTRUCTION 400
      EF_RUNTIME 300

The index uses the HNSW algorithm with cosine distance. M=64 with EF_CONSTRUCTION=400 builds a denser graph for higher recall, and EF_RUNTIME=300 widens the search at query time. The index is created automatically on first use, and rebuilt if its parameters change.
